# lint_test.py (분류기, 전문가 분석 chain)

명령: 금방전에 레오가 왜 실행 실패를 했지?

## 👔 CEO 종합

원인: 레오 코드 내 `/usr/local/...` 하드코딩된 **절대 경로** 때문 (빌드/린트 통과 후 런타임에 터지는 전형적 안티패턴).

해결: 절대 경로 전부 **프로젝트 루트 기반 상대 경로**로 교체. `path` 모듈 쓸 때 항상 `process.cwd()`나 `__dirname` 조합하는 습관 들이기.

방지: 향후 코드 검사 시 파일 경로 하드코딩 부분 코다리가 사전 포착하도록 프로세스 추가.

## 🧠 💻 코다리 추가 인사이트

💻 코다리: 레오의실행 실패 원인 추적해봤습니다. 결론부터 말하면 '경로 불일치' 하나입니다.

**[원인 진단]**
- **어디서:** `0756/error1.txt`와 `0832/failure_trace.log`를 비교해보니 원인이 한눈에 들어옵니다.
- **무엇이:** 레오의 코드 내부에 `/usr/local/.../app/api/route.ts`라는 하드코딩된 경로가 박혀 있습니다.

**[왜 실패했나]**
1. **경로 오염 (Path Contamination):** `0756/error1.txt`에선 `ENOENT: no such file or directory, OPENPATH='/usr/local/234/.../app/api/route.ts'`가 찍힙니다. `/usr/local/234`라는 숫자는 코더의 로컬 머신 경로에서 흘러 들어온 겁니다 — **프로젝트를 다른 환경으로 옮기거나 컨테이너화할 때 절대 경로가 포함되면 무조건 터지는 전형적인 안티패턴**입니다.
2. **어떻게 재현되나:** 레오가 코드를 작성/수정할 때 상대 경로 대신 현재 작업 중인 호스트의 전체 경로를 문자열로 박아넣었습니다. `0832`의 트레이스도 정확히 그 지점을 가리킵니다.
3. **왜 발견이 늦어졌나:** 빌드(npm run build)와 린트(lint)는 단순 문법/타입 검사라 파일 시스템 경로까지는 걸러내지 못합니다. 이건 '런타임'에 파일 열 때 터지는 거라 배포 직전이나 실행 시점에야 드러나는 거죠.

**[수정 방향]**
- 해당 하드코딩된 전체 경로를 **프로젝트 루트 기준의 상대 경로**로 전부 교체하면 해결됩니다. `path` 모듈을 쓸 때는 항상 `process.cwd()`나 `__dirname` 기반의 상대 경로를 조합하는 데 습관 들여야 하고요.

**[동일 사례 예방]**
- 앞으로 코드 베이스 전수 검사 때 파일 경로가 하드코딩된 부분은 나부터 잡아낼 겁니다. 절대 경로는 시스템이 결정하게 내버려 두는 게 정답이니까요.
